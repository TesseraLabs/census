## Context

В коде Census уже есть неявная ось чувствительности объявляемых объектов: гранты из
каталога несут risk-метку и привязку к мерам; `groups`/`sudo_role`/`limits` — «сырые»
перечислимые примитивы; inline `payload.sudo` и исполняемые файловые гранты способны к
эскалации. Сегодня ось выражена двумя предупреждениями (`RawPrimitiveAlongsidePermissions`,
`InlineSudoUnlabeled`) — данными для ревьюера, не гейтом. Два соседних change'а
(`manifest-fragments`, `enumerable-domains`) и модель «полный профиль по умолчанию,
ослабление только явным решением» требуют ту же ось как enforce-механизм.

## Goals / Non-Goals

**Goals:**
- Единая вычисляемая шкала классов эффектов для всех объявляемых объектов.
- Fail-closed гейт политики до любых мутаций (симметрично гейтам подписи и anti-lockout).
- Отчётность класса каждого объекта в plan/apply (человеку и в JSON).
- Совместимость: без `[policy]` поведение неотличимо от текущего.

**Non-Goals:**
- Не вводим подписанные исключения (Deviation Manifest) — это отдельный будущий change
  поверх шкалы.
- Не меняем состав каталога и risk-метки.
- Не классифицируем объекты чужих (не-Census) источников — только объявленное в
  декларации.

## Decisions

### D1. Класс вычисляется, не декларируется

Класс объекта выводится из его природы (тип объекта + признаки: каталожность,
исполняемость файлового гранта, inline sudo), автор декларации не может его указать.
Альтернатива «автор помечает класс сам» отвергнута: самодекларация чувствительности —
приглашение врать; политика, читающая ложные метки, хуже отсутствующей.

### D2. Шкала из трёх присваиваемых классов + одно имя-запрет

`curated < raw < escalation`; `unbounded` — имя класса, который не присваивается ни
одному объекту: объекты с неограниченным эффектом в модель Census не входят вовсе
(граница держится на уровне допуска доменов, см. `enumerable-domains`). Имя нужно,
чтобы политика и делегации могли явно говорить «такого не бывает и не будет», а
документация — называть границу. Альтернатива «шкала из четырёх рабочих классов»
отвергнута: рабочий класс подразумевает возможность разрешить, а разрешаемого
unbounded в Census нет по построению.

### D3. Порядок и политика: `max_effect_class`

Классы упорядочены; политика — один ключ `[policy] max_effect_class = "curated"|"raw"|
"escalation"`. Отсутствие секции = нет ограничения (текущее поведение, предупреждения
остаются). Альтернатива «список запрещённых классов» отвергнута: шкала монотонна по
чувствительности, разрешать `escalation`, запрещая `raw`, бессмысленно — а линейный
максимум невозможно неправильно сочетать.

### D4. Гейт стоит в resolve→plan, отказ до снапшота

Нарушения собираются на этапе резолва (там, где сегодня рождаются предупреждения) и
приводят к отказу `plan`/`apply` со списком: роль, объект, класс, разрешённый максимум.
Отказ происходит до снапшота и до любых мутаций — симметрично отказу по подписи.
Штатный `plan` при нарушении тоже падает (не «показать план и предупредить»):
план, который заведомо нельзя применить, вводит в заблуждение.

### D5. JSON и golden-контракты — аддитивно

`effect_class` добавляется полем в существующие объекты plan-JSON; секция `[policy]` —
новая необязательная секция строгого парсера. Существующие golden-снимки остаются
валидными; новые фиксируют поле и секцию.

## Risks / Trade-offs

- **Порог у «исполняемости» файлового гранта.** Классификация executable-грантов зависит
  от прав/типа целевого файла; правило должно быть консервативным (сомнение → более
  высокий класс) и зафиксированным тестами, иначе граница классов дрейфует.
- **Соблазн расширять шкалу.** Каждый будущий домен обязан раскладываться в три класса;
  появление «полутонов» (custom-классов) размоет политику — запрещено спекой.
- **Совместимость предупреждений.** Старые warnings остаются в режиме без политики;
  дублирование «warning + отказ» в режиме с политикой не допускается (одно событие — одна
  форма).
