## Why

Между «пакеты установлены» и «машина стала конкретным устройством» лежит device-state:
sysctl, модули ядра, состояние systemd-юнитов, парольные политики, доверенные ключи,
hostname, флаги монтирования. Сегодня его некому применять декларативно: Census ограничен
объектами доступа, апдейтер по своему дизайну декларативным движком состояния не является,
а банковские стандарты (живой пример — стандарт настроек безопасности банкоматов на Astra
Linux 1.8 одного из банков: ~25 sysctl-контролей, 12 blacklist-модулей, десятки
key→value-политик, права и аудит) требуют управлять всем этим воспроизводимо и с
привязкой к мерам. Расширяем Census — но по операционному критерию допустимости, который
держит границу продукта: Census растёт предметной областью, не превращаясь в
универсальный конфиг-менеджмент.

## What Changes

- Фиксируется **критерий допустимости домена** (проверяется для каждого нового домена до
  его принятия): (1) объекты перечислимы до применения; (2) есть маркер принадлежности —
  чужое не трогается; (3) обратная операция определена так же строго, как прямая;
  (4) объекты сопоставимы с мерами (`framework-crossref`); (5) у каждого типа объекта
  определён класс эффекта (`effect-classes`). Домен с произвольным (unbounded)
  содержимым не допускается — граница, за которой провижинер становится «Ansible с
  типами». Важно: unbounded — про **эффекты**, не про байты (баннер `/etc/issue` —
  произвольный текст с ограниченным эффектом; строка конфига демона — нет).
- **Курируемый слой контролей — главное содержание change'а.** По образцу того, как
  каталог прав раскрывает человеко-понятное право в группы/sudo/файловые гранты, вводится
  каталог **контролей безопасности**: контроль с человеческим именем, описанием риска,
  привязкой к мерам (ГОСТ Р 57580, PCI DSS, SWIFT CSP, ФСТЭК) раскрывается в набор
  объектов доменов. Декларация объявляет контроли, не ключи:
  `controls = ["disable-legacy-filesystems", "restrict-core-dumps", "harden-network-stack"]`
  вместо перечисления двенадцати `blacklist`-строк и двадцати пяти sysctl-ключей.
  Голый ключ остаётся доступен как escape hatch класса `raw` — ровно как сегодня
  сосуществуют `permissions` и сырые `groups`/`sudo_role`.
- **Обобщённый kv-движок** как механика под слоем контролей: типизированные key→value-цели
  описываются **словарями-данными** в каталожном дереве (`/usr/share/census/`): имя
  ключа, тип и допустимые значения, целевой файл/механизм применения, класс эффекта,
  привязка к мерам, l10n. Движок один; добавление цели = добавление словаря, не кода.
  Словари первой волны: **sysctl** (`/etc/sysctl.d/` + runtime), **login-policy**
  (`login.defs`), **pwquality**, **faillock**, **sshd** (`sshd_config.d/`, включая
  ограниченные Match-блоки).
- Домены со своей механикой (не kv):
  - **modules**: blacklist/запрет автозагрузки модулей ядра через маркированный файл в
    `/etc/modprobe.d/` (+ выгрузка при применении); класс `raw`, для курируемого списка
    небезопасных ФС/протоколов — `curated`.
  - **units**: только состояние юнита — enable / disable / mask (содержимое юнитов и
    drop-in'ов — вне домена как unbounded).
  - **trust-anchors**: типизированные наборы публичных ключей по назначению; класс
    `escalation`. Бутстрап-якорь самого Census (`/etc/census/trust.pub`) структурно вне
    managed — по образцу rescue/anti-lockout.
  - **identity**: hostname и связанная запись hosts.
  - **mounts**: опции монтирования из белого списка (`nodev,nosuid,noexec,ro,bind`) для
    явно перечисленных точек, включая bind-точки (пример из банковского стандарта:
    `/tmp /tmp none defaults,bind` для исключения из перехвата).
- Anti-lockout расширяется на новые домены: план, снимающий последний путь доступа
  (сеть/SSH-параметры, faillock root, mask сервиса удалённого доступа), отклоняется той
  же семантикой, что и сегодняшняя защита rescue-учётки.
- Кандидаты второй волны фиксируются списком (не реализуются): GRUB cmdline, правила
  auditd, chrony/время, afick-список целостности, Astra-тумблеры (`astra-*`), баннеры.
  Процедурные контроли стандартов («убедитесь, что…»: уникальность UID, пустая группа
  shadow, отсутствие `.netrc` и пр.) — трек расширения `provisioning-doctor` /
  `exposure-audit`, не доменов материализации.

## Capabilities

### New Capabilities
- `security-controls`: курируемый каталог контролей безопасности — контроль, его риск,
  привязка к мерам, раскрытие в объекты доменов, l10n; объявление контролей в декларации;
  отчёт «какие контроли выполнены, какие частично, какие не покрыты».
- `domain-admission`: критерий допустимости домена и обязательства каждого домена
  (перечислимость, маркер, обратная операция, меры, классы).
- `domain-kv`: движок типизированных key→value-целей со словарями-данными; словари
  первой волны: sysctl, login-policy, pwquality, faillock, sshd.
- `domain-modules`: запрет модулей ядра (blacklist + install /bin/true) как
  managed-объекты.
- `domain-units`: декларация и материализация состояния systemd-юнитов.
- `domain-trust-anchors`: декларация и материализация типизированных наборов доверенных
  ключей.
- `domain-identity`: декларация и материализация hostname/идентичности.
- `domain-mounts`: декларация и материализация опций монтирования (включая bind) для
  перечисленных точек.

### Modified Capabilities
- `provisioning-apply`: конвейер (снапшот, порядок фаз, отчёт) расширяется на новые
  домены; anti-lockout дополняется страховкой «последнего пути доступа» для
  сети/SSH/faillock/units.

## Impact

- Код: слой контролей (раскрытие control → объекты доменов, по образцу catalog-resolution);
  kv-движок + словарная загрузка (по образцу catalog/l10n/framework-деревьев);
  модули units/modules/trust-anchors/identity/mounts; `src/declaration.rs` (новые
  секции), `src/plan.rs`/`src/apply.rs`/`src/backup.rs` (фазы, снапшоты),
  `src/state.rs` (новые типы managed-записей).
- Данные: каталог контролей + словари kv-целей и курируемые списки (sysctl безопасности,
  небезопасные модули) с привязкой к мерам и l10n — новое каталожное дерево, публичный
  контракт форматов контроля и словаря. Первичное наполнение — по банковским стандартам
  настройки Astra-банкоматов.
- Контракты: golden-тесты декларации и JSON plan расширяются аддитивно.
- Источник требований для словарей: банковские стандарты настройки (ГОСТ Р 57580,
  PCI DSS 4.0.1, СЗИ-рекомендации ФСТЭК) — словари ссылаются на меры через
  `framework-crossref`.
- Зависит от change `effect-classes`; сочетается с `manifest-fragments` (фрагменты могут
  объявлять объекты новых доменов в рамках скоупа делегации).
