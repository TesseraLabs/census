# Tasks: enumerable-domains

Rust через `rust-pro`, срезами, TDD. На каждый срез: `cargo test` + `cargo clippy
--all-targets --all-features` зелёные, ревью `master-code-reviewer`. Коммит/PR — вне
рабочего окна (08:00–19:00 МСК). Зависит от `effect-classes`.

Порядок разделов подчинён одному правилу: **первым делается сквозной срез** (один контроль
→ один домен → применение → отчёт), а не пять доменов подряд. Только сквозной срез
показывает, что слой контролей не разъезжается с механикой.

Живой источник требований для наполнения каталога — банковские стандарты настройки
Astra-банкоматов (образец изучен: ~25 sysctl-контролей, 12 запретов модулей, kv-политики,
состояния служб, точки монтирования).

## 1. Критерий допустимости (спека прежде кода)

- [ ] 1.1 Зафиксировать в доке пять условий и процедуру: новый домен проходит проверку на
      ревью спеки, а не в коде.
- [ ] 1.2 Прогнать через критерий домены первой волны и записать результат по каждому
      (включая явный отказ для «произвольный конфиг службы»).
- [ ] 1.3 Записать список кандидатов второй волны с отметкой, какое условие у каждого пока
      не выполнено: GRUB cmdline, правила аудита, синхронизация времени, список
      целостности, тумблеры Astra, баннеры.

## 2. Сквозной срез: контроль → sysctl → отчёт

- [ ] 2.1 Формат каталога контролей: идентификатор, риск, привязка к мерам, раскрытие в
      объекты; тексты — в дерево l10n (структурный файл без человекочитаемых строк).
- [ ] 2.2 Формат словаря kv-цели: ключи, типы, допустимые значения, механизм применения,
      класс эффекта на ключ, привязка к мерам, версия схемы.
- [ ] 2.3 kv-движок: разбор словаря, валидация ключа и значения, диff, снапшот, применение,
      снятие. Цель `sysctl`: маркированный drop-in + runtime-применение.
- [ ] 2.4 Раскрытие контроля в объекты; объявление контролей в декларации; отказ на
      неизвестном идентификаторе.
- [ ] 2.5 Различение объявлено / записано / действует в отчёте; ключ, требующий
      перезагрузки, не показывается действующим.
- [ ] 2.6 Отчёт о состоянии контроля: выполнен / частично / не выполнен + объекты,
      определившие вердикт.
- [ ] 2.7 Сырой ключ мимо контроля: работает, помечен некурируемым, класс не ниже `raw`.
- [ ] **Гейт среза:** один реальный контроль из банковского стандарта (например ограничение
      ptrace) применяется от объявления до отчёта на живой Astra.

## 3. Остальные kv-словари

- [ ] 3.1 `login-policy` (`login.defs`): сроки действия паролей и предупреждения.
- [ ] 3.2 `pwquality`: длина, классы символов, enforce-политики.
- [ ] 3.3 `faillock`: порог блокировки и время разблокировки.
- [ ] 3.4 `sshd` (drop-in): аутентификационные тумблеры, криптонаборы, ограниченные
      Match-блоки (только перечислимые директивы; произвольные — вне домена).
- [ ] 3.5 Проверить, что ни один словарь не потребовал изменений движка (если потребовал —
      это сигнал о неверной границе, разобрать до продолжения).

## 4. Домены со своей механикой

- [ ] 4.1 `modules`: маркированный файл (`blacklist` + подмена загрузки), попытка выгрузки,
      «занят → требуется перезагрузка» как штатный исход, чужие записи не трогаются.
- [ ] 4.2 `units`: enable / disable / mask; состояние читается из системы; содержимое
      юнитов вне домена.
- [ ] 4.3 `mounts`: белый список опций, bind-точки (случай «каталог связан сам с собой»),
      персистентность между перезагрузками, конфликт владения с `units` → отказ.
- [ ] 4.4 `identity`: имя узла + согласованная локальная запись разрешения имён, валидация
      синтаксиса.
- [ ] 4.5 `trust-anchors`: наборы по назначению, класс `escalation`, валидация материала
      ключа, запрет управления собственным корнем Census.

## 5. Конвейер и защита

- [ ] 5.1 Фиксированный порядок применения доменов (kv → modules → mounts → units →
      identity → trust-anchors → доступ); тест детерминизма.
- [ ] 5.2 Anti-lockout «последнего пути доступа»: маскирование единственной службы доступа,
      отключение сети, снятие несущей точки монтирования.
- [ ] 5.3 Осознанный отказ от страховки — предусмотренным способом, с фиксацией в отчёте.
- [ ] 5.4 Снапшот и восстановление для всех новых типов файлов.

## 6. Наполнение каталога и связь с мерами

- [ ] 6.1 Первичный набор контролей по изученному банковскому стандарту: небезопасные ФС и
      протоколы, ограничение core dumps, защита ссылок и FIFO, ptrace, сетевые параметры,
      парольные политики, отключение неиспользуемых служб.
- [ ] 6.2 Привязка каждого контроля к мерам (ГОСТ Р 57580, PCI DSS, SWIFT CSP, требования
      ФСТЭК) через существующий кросс-референс; ключ без меры допускается только с явным
      обоснованием, не молчанием.
- [ ] 6.3 Отчёт покрытия: какие контроли каталога объявлены, какие нет — расширение
      существующего отчёта покрытия, без изменения его контракта.
- [ ] 6.4 Проверить на живой Astra, что применение контролей не ломает вход по
      удостоверению (совместная работа с PAM-стеком, которым Census не владеет).

## 7. Документация

- [ ] 7.1 Раздел «контроль вместо ключа»: почему декларация пишется в терминах контролей и
      когда допустим сырой ключ.
- [ ] 7.2 Раздел о критерии допустимости домена — для тех, кто будет предлагать новые.
- [ ] 7.3 Честная граница отчёта: применённое ≠ проверенное; процедурные требования
      стандартов закрываются проверками, а не материализацией.
