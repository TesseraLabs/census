# usb-storage-policy — декларативная политика USB-носителей

## ADDED Requirements

### Requirement: Объект декларации политики носителей
Декларация ДОЛЖНА (MUST) поддерживать объект политики USB-носителей с режимами:
`unrestricted` — политика не управляется census; `storage-blocked` — устройства класса
mass-storage не подключаются, прочие классы (смарт-карты и CCID-интерфейсы, клавиатуры,
сетевые адаптеры) не затрагиваются; `allowlist` — подключаются только перечисленные
устройства по признакам вендора и продукта. Режим ДОЛЖЕН (MUST) описывать желаемое
состояние, а не инструмент его достижения: имя провайдера в декларации указываться
НЕ ДОЛЖНО (MUST NOT).

#### Scenario: Токен продолжает работать при заблокированном storage
- **WHEN** применён режим `storage-blocked` и в порт вставлен CCID-токен
- **THEN** токен доступен смарт-картному стеку; флеш-накопитель в тот же порт не монтируется

#### Scenario: Попытка задать провайдера в декларации
- **WHEN** декларация указывает конкретный механизм блокировки
- **THEN** разбор декларации отвергает поле: инструмент — свойство системы, не декларации

### Requirement: Провайдеры за единым SPI
Реализация политики ДОЛЖНА (MUST) выполняться провайдером за единым SPI (`modprobe`-блэклист,
USBGuard, штатный контроль устройств Astra). Провайдер ДОЛЖЕН (MUST) выбираться по
фактическому составу системы. Отсутствие пригодного провайдера ДОЛЖНО (MUST) приводить к
внятному отказу на этапе плана; молчаливый no-op ЗАПРЕЩЁН (MUST NOT) — иначе система
выглядит защищённой, не будучи ею.

#### Scenario: Ни одного пригодного провайдера
- **WHEN** в системе нет ни USBGuard, ни штатного контроля устройств, а требуемый режим
  ими не достигается
- **THEN** план завершается отказом с указанием, чего не хватает; apply не запускается

### Requirement: План, применение и откат
Изменение политики ДОЛЖНО (MUST) проходить те же фазы, что остальные объекты: план
показывает разницу между фактическим и желаемым состоянием, apply атомарен и при ошибке
любой фазы восстанавливает прежнее состояние из снапшота, завершаясь ненулевым кодом.
Повторное применение той же политики ДОЛЖНО (MUST) быть идемпотентным.

#### Scenario: Сбой в середине применения
- **WHEN** применение политики прервано ошибкой после частичного изменения конфигурации
- **THEN** прежнее состояние восстановлено из снапшота, система осталась согласованной

### Requirement: Проверка фактического состояния в doctor
`doctor` ДОЛЖЕН (MUST) проверять не наличие конфигурационных файлов, а фактическое
состояние: соответствует ли поведение системы объявленному режиму. Расхождение между
объявленным и фактическим ДОЛЖНО (MUST) сообщаться как дрейф с указанием провайдера.

#### Scenario: Политика объявлена, но не действует
- **WHEN** конфигурация провайдера на месте, но модуль storage загружен и устройства
  монтируются
- **THEN** doctor сообщает дрейф, а не «всё в порядке по файлам»

### Requirement: Anti-lockout при блокировке носителей
`apply` ДОЛЖЕН (MUST) отказывать, если применение политики отрезает единственный доступный
путь управления системой, по тем же правилам, что anti-lockout для роль-учёток. Спека и
документация ДОЛЖНЫ (MUST) фиксировать: обратное включение выполняется новой декларацией,
доставленной каналом, не зависящим от mass-storage, — иначе блокировка становится
необратимой на удалённом объекте.

#### Scenario: Единственный путь управления — съёмный носитель
- **WHEN** применение `storage-blocked` отрезало бы единственный канал доставки деклараций
- **THEN** apply отказывает с диагностикой; политика не применяется
